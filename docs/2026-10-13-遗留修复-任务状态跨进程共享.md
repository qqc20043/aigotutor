## 一、问题回顾

任务表 `_TASKS` 是进程内字典。多 worker 部署下的具体故障：

| 场景 | 修复前 |
|---|---|
| 提交任务落在 worker A，轮询 `/api/tasks/{id}` 被负载均衡到 worker B | **404**（B 的字典里没有） |
| 任务列表 `GET /api/tasks` 落在别的 worker | 只看得到本进程的任务 |
| 从别的 worker 取消任务 | **打不到任务真正所在的进程**，取消无效 |

## 二、核心设计：执行不迁移，只镜像可观测性

**关键判断**：asyncio 任务句柄**无法跨进程传递**。若要让任务在任意 worker 上执行，
就必须引入 broker + 序列化 + 重试语义（即 Celery 那一套）—— 对"秒级到十秒级"的任务
来说是过度设计，且会显著抬高部署成本。

因此分工是：

```
执行  → 留在创建它的进程（owner）
状态/事件/取消信号 → 镜像到 Redis，任何 worker 都能读、能取消
```

这正是 `core/task_store.py` 的职责边界：**只做镜像，不碰执行**。

### 键设计

```
{prefix}:task:{tid}:state    JSON 状态快照
{prefix}:task:{tid}:events   事件列表（RPUSH 追加，LRANGE 按索引增量读）
{prefix}:task:{tid}:cancel   取消信号（owner 轮询它）
{prefix}:task:{tid}:owner    所属 worker 标识（诊断用）
{prefix}:tasks:user:{uid}    用户任务索引（ZSET，score=创建时间）
```

全部带 TTL（1 小时，与 `tasks.cleanup` 的默认 max_age 对齐）—— 不需要额外的清理逻辑，
任务结束后键自然过期。

## 三、三个实现要点

### 1. 跨进程取消：信号 + owner 轮询（而非 pub/sub）

```python
# 发起方（任意 worker）
def cancel(task_id):
    task = _TASKS.get(task_id)
    if task is not None:  # 本地有 -> 直接取消
        task.cancel_requested = True
        task.handle.cancel()
        return True
    state = task_store.read_state(task_id)  # 本地没有 -> 别的 worker 的任务
    if state is None or state["status"] in terminal:
        return False
    return task_store.request_cancel(task_id)  # 写信号
```

```python
# owner 侧：轮询信号并取消本地句柄
async def _watch_remote_cancel(task, interval=1.0):
    while True:
        await asyncio.sleep(interval)
        if task_store.is_cancel_requested(task.id):
            task.cancel_requested = True
            task.handle.cancel()  # 句柄只有 owner 能用
            return
```

**为什么用轮询而不是 pub/sub**：取消是低频操作，轮询实现简单，且不需要维护订阅连接的
生命周期 —— 订阅断了会**静默失效**（消息丢失无感知），反而更难排查。1 秒间隔对
"用户点取消"这个交互足够及时。

### 2. SSE 事件流的双路径

| 任务位置 | 数据源 | 延迟 |
|---|---|---|
| 本进程（owner） | 内存 deque | 最低（原实现不变） |
| 别的 worker | Redis 事件列表（LRANGE 增量） | 略高（0.5s 轮询间隔，用户无感） |

非 owner 路径的收尾判定用 **"事件读完 + Redis 状态是终态"两个条件同时满足** ——
任务结束与终态事件写入之间有极短窗口，只看状态会漏掉最后的 `done` 事件。

### 3. 终态必须镜像（否则别处永远看到 running）

```python
finally:
    task.finished_at = time.time()
    if task.handle is not None:
        task.handle = None
    task_store.publish_state(task)   # ← 这一行不能漏
```

这是最容易漏的一处：只在状态变化时镜像、忘了在 `finally` 里补终态，
结果是别的 worker 永远看到 `running`，前端进度条永远转圈。

## 四、API 层的修正

`app/api/agent.py` 里三处原本用 `get_task()`（只查本进程字典）：

```python
# 修复前
task = get_task(task_id)  # 多 worker 下随机 404
if task is None:
    raise HTTPException(404, "任务不存在")

# 修复后
snapshot = task_detail_snapshot(task_id)  # 本地优先，否则读 Redis 镜像
if snapshot is None:
    raise HTTPException(404, "任务不存在")
```

`get_task()` 保留（返回对象，供需要操作句柄的内部代码用），但 API 层统一走
`task_detail()`（返回快照，跨进程可见）。

## 六、遗留与注意

1. **取消有最多 1 秒延迟**：owner 侧轮询间隔为 1 秒。这是刻意的取舍（见 §三.1），
   若需要更快可调 `_watch_remote_cancel(interval=...)`，但会增加 Redis 往返。

2. **镜像失败不影响任务执行**：`task_store` 的所有写操作都包了 try/except 并降级为
   debug 日志 —— 镜像只是可观测性增强，不能因为 Redis 抖动让任务本身失败。

3. **用户索引会累积已过期任务**：`cleanup_expired_index()` 在 `list_tasks` 时顺手清理，
   避免 `zrevrange` 取到的都是无效 id。索引本身也有 TTL 兜底。

4. **仍未做的**：任务**执行本身**的跨 worker 均衡（即"提交到 A、在 B 上执行"）。
   需要 broker + 序列化 + 重试语义，属于 Celery 范畴，当前规模不需要。
   若将来任务变长（分钟级）或需要独立扩缩容，再引入。
