## 一、解题提示 Agent（`agents/hint.py`）

### 设计要点：强度是策略，内容是表达

强度**不是模型决定的**，而是由规则层按该题知识点掌握度算定后写进 prompt：

```python
# core/rules.py
HINT_STRENGTH_THRESHOLDS = [(40.0, "pseudocode"), (65.0, "key_observation"), (100.0, "direction")]


def hint_strength_for(mastery_score, attempts):
    if attempts <= 0:
        return "pseudocode", "该知识点尚无提交记录（0 次），首次接触给最强提示。"
    if attempts < 3:
        return (
            "key_observation",
            f"该知识点仅 {attempts} 次提交，样本不足以判断掌握度，保守给中等强度提示。",
        )
    ...
```

三档递进：

| 掌握度 | 强度 | 给什么 |
|---|---|---|
| < 40 或首次接触 | `pseudocode` | 3 步以内伪代码级骨架 |
| 40 – 65 | `key_observation` | 关键性质 + 需检查的边界 |
| >= 65 | `direction` | 只给方向 |

**为什么样本不足要保守升档**：只做过 1-2 次的题，掌握度数字本身不可信（可能因一次偶然 AC 虚高），
照数字给弱提示会让新手卡死。`attempts == 0` 直接给最强。

**为什么强度归规则、不归模型**：掌握度是数据库里的客观事实。让模型"看着办"会导致同一用户同一题
在不同时间拿到不同强度，既不可复现也无法评测。`postprocess` 会把模型给的强度强制改回，
并补齐条数（条数与强度绑定，多给少给都破坏语义）。

**提示的边界**：绝不输出可提交的完整代码 —— 一旦给出完整解法，训练价值归零。system prompt 里明确禁止。

### 接口

```
POST /api/problems/{id}/hint?language=python&current_code=...
```

返回 `strength` / `hints[]` / `key_insight` / `next_step` / `strength_reason` / `memory_tokens`。

## 二、复习队列优先 Agent（`agents/review.py`）

### 设计要点：与 FSRS 职责分离

| 组件 | 回答的问题 | 学科属性 |
|---|---|---|
| FSRS（`core/fsrs.py`） | **何时**该复习（间隔多长、何时到期） | 记忆科学 |
| 本 Agent | 到期后**先做哪个**（排序 + 解释） | 学习策略 |

**为什么不把优先级写进 FSRS**：混在一起会让 FSRS 参数被业务策略污染，无法独立评估与调参。

排序公式（权重写在规则层，可复现）：

```
score = 逾期天数 × 3 + (100 - 最弱知识点掌握度) × 0.8 + 遗忘次数 × 6
```

权重是刻意选的量级：逾期天数通常 0-10、掌握度缺口 0-100、遗忘次数 0-3，乘完权重后三者都有实际影响，不会互相淹没。

**时间预算硬约束**：每题按 15 分钟估，超出预算截断 —— 宁可少挑，也不给用户一个做不完的队列。
截断后 `order` 重新编号（前端直接按 order 渲染）。

`postprocess` 会过滤模型编造的题目（只允许在候选内重排），与 `RecommendAgent` 同一思路。

### 接口

```
GET /api/review/priority?time_budget_minutes=60
```

与 `/review/queue` 同源：queue 是**按到期时间**排的客观队列，priority 是**按学习收益**重排的推荐顺序。

## 三、学习记忆注入（`core/memory.py`）

### 核心设计：注入的不是历史，是结论

刷了 200 题的用户，原始历史（全部提交 + 全部错题 + 全部对话）轻松超过 10 万 token。
但模型真正需要的从来不是"他做过哪些题"，而是：

> 他现在哪里弱、什么错误模式反复出现、最近是上升还是下滑。

`MemorySnapshot` 只保留三类**会改变 Agent 决策**的事实：

| 来源 | 字段 | 用途 |
|---|---|---|
| 掌握度画像 | `weak_tags` / `strong_tags` | 决定推荐难度与提示强度 |
| 错题本 + 聚类 | `error_patterns` | 决定该重点练什么 |
| 提交时间序列 | `recent_verdicts` / `trend` | 决定状态是上升还是下滑 |

### Token 可控（本轮可量化的成果）

```
实测：81 次提交的用户 → 注入块约 87 token
```

**注入量与会话规模解耦**：刷 10 题与刷 1000 题，注入量基本恒定（只有数字位数差异）。
回归测试 `test_memory_token_budget_independent_of_history_size` 守护这条契约。

### 注入范围

```python
class BaseAgent:
    inject_memory: bool = False   # 默认不注入

# 决策类 Agent 显式开启（需要用户历史状态）
hint / recommend / review / roadmap  → inject_memory = True
# 能力型 Agent 保持关闭（注入只会增加 token 与干扰）
judge / difficulty / solution / quality → False
```

记忆块拼在 prompt **前面**（背景先行，模型遵从度更高），由 `with_memory()` 统一处理。

### 趋势判定

```python
def _classify_trend(verdicts):
    if len(verdicts) < 4:
        return "unknown"
    # 前后半段通过率对比（不用线性回归：10-20 条数据拟合斜率对单次波动过敏）
    delta = recent_rate - older_rate
    return "rising" if delta > 0.15 else "falling" if delta < -0.15 else "steady"
```

阈值从 6 改到 4：**全通过/全失败本身就是最清晰的趋势**，不该被样本量门槛挡掉
（这是测试发现的真实边界问题）。

## 四、代码质量两阶段评分（`agents/quality.py`）

### 两阶段分工

| 阶段 | 负责 | 内容 |
|---|---|---|
| 第一阶段（规则，**确定性问题**） | `rules.quality_window` | 嵌套深度、代码行数、标识符长度分布、注释比例、边界判断密度 |
| 第二阶段（LLM，**开放性问题**） | `agents/quality.py` | 可读性观感、边界是否真的周全、命名是否表达意图 |

**硬约束**：模型只能在规则基线 ±12 分内修正，越界无条件夹回（`clamp_quality`），等级随夹紧后的分数重算。

### 修掉的一个评分偏差（测试发现）

早期实现把**任意 `if`** 都算作"边界处理"，导致深嵌套代码因分支多而拿到"合格"档：

```
修复前：规范代码 79.8 vs 深嵌套+单字母 68.9   ← 区分度不足
修复后：规范代码 73.5 vs 深嵌套+单字母 54.0   ← 区分度明确
```

改为匹配**具体的边界语义**（`if not x` / `== 0` / `try` / `assert` / `is None` / `INT_MAX` 等 15 种模式）。

### 与判题的分工

判题管"对不对"（AC/WA/TLE），质量评分管"好不好"。**只有 AC 的代码才值得评质量** —— 错代码谈可读性没有意义。

## 五、修掉的一个真实缺陷（记忆注入破坏 mock 解析）

### 现象

提示接口返回的 `strength` 是 `pseudocode`，但 `strength_reason` 却说"掌握度 52 分（4 次提交），
据此给出关键观察级提示"——**强度与依据不一致**，且文案是写死的。

### 根因

`with_memory()` 把记忆块拼在 prompt 前面后，`MockProvider._parse_payload` 的 `json.loads` 失败：

```python
# 修复前
def _parse_payload(user):
    try:
        data = json.loads(user)  # prompt 现在以 "【学习记忆】" 开头 → 抛异常
        return data if isinstance(data, dict) else {}
    except (json.JSONDecodeError, TypeError):
        return {}  # 静默返回空 → 回退到静态 FIXTURES
```

于是 mock 忽略了本次真实上下文，永远返回 fixture 里写死的那条文案。

**这个 bug 只在"记忆注入 + mock provider"组合下出现** —— 单测容易漏，因为单测直接传 JSON。

### 修法

```python
def _parse_payload(user):
    try:
        data = json.loads(user)
        if isinstance(data, dict):
            return data
    except (json.JSONDecodeError, TypeError):
        pass
    # 退化路径：剥离前缀（记忆块）与后缀
    start, end = user.find("{"), user.rfind("}")
    if start >= 0 and end > start:
        try:
            data = json.loads(user[start : end + 1])
            if isinstance(data, dict):
                return data
        except (json.JSONDecodeError, TypeError):
            pass
    return {}
```

回归测试 `test_mock_parses_prompt_with_memory_prefix` 守住它。

   影响很小（记忆只影响表达不影响强度），但值得知道。
