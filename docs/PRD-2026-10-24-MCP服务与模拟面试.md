## 一、Feature A：MCP Server 封装

### A1. 背景与目标

2026 年 MCP（Model Context Protocol）已成为 AI 应用与外部系统互操作的主流
协议（Claude Desktop / Cursor / 各类 Agent 宿主均支持）。把平台的教练能力
暴露为 MCP 工具后，用户可以在宿主 AI 里直接问"我今天该刷什么题"，由宿主
调用本平台的工具拿到带理由的推荐。

**目标**：
1. 平台能力以 MCP 工具形式可被任意 MCP 宿主调用（Web 与 MCP 双形态）；
2. 工具设计自包含（输入输出 schema 清晰、返回内容含可解释理由），
   让"无上下文的宿主 AI"也能把结果讲清楚；
3. 治理策略在 MCP 路径同样生效：提示强度仍由规则层按掌握度算定，
   模型（此处是宿主 AI）无权升降档。

**非目标（v1 明确不做）**：
- 不做远程 HTTP/SSE 传输（只做 stdio 本地宿主）；多用户/多租户鉴权；
- 不做资源订阅（resources/prompts 原语），只做 tools；
- 不在 MCP 里暴露管理后台与用户管理类操作。

### A2. 架构决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 进程形态 | **独立进程 `scripts/mcp_server.py`，与 Web 共享同一 SQLite 库** | MCP 是本地宿主拉起的进程；SQLite WAL 支持多进程读写；复用 service 层保证两条路径行为一致 |
| 传输 | stdio | Claude Desktop/Cursor 本地配置的标准形态，零网络面 |
| 身份 | 环境变量 `AIGOTUTOR_MCP_USER`（默认 `demo`） | 本地单用户场景；服务启动时校验用户存在，不存在则启动失败并提示（明确报错优于静默用错人数据） |
| LLM 配置 | 复用 `.env`/环境变量体系（`AIGOTUTOR_PROVIDER` 等） | 与 Web 同一套用户级模型配置读取逻辑 |
| 依赖 | `mcp`（FastMCP）进 requirements.txt | 官方 Python SDK；缺失时 Web 不受影响（仅 MCP 入口不可用） |

### A3. 工具清单（11 个）

> 命名统一 `aigotutor_` 前缀避免与宿主内其它工具撞名；每个工具返回都带
> `reason`/`explanation` 类字段（可解释性是平台一贯承诺）。

| # | 工具名 | 输入 | 输出要点 | 底层映射 |
|---|---|---|---|---|
| 1 | `aigotutor_next_problem` | `target_score?` | 推荐题目 + 理由（点名掌握度数字） | `pipeline.recommend_next` + `services.list_problems` 构造候选 |
| 2 | `aigotutor_get_hint` | `problem_id`, `attempts?` | 三档渐进提示，strength 注明由掌握度算定 | `pipeline.generate_hint`（无会话状态，单发口径） |
| 3 | `aigotutor_similar_problems` | `problem_id`, `limit?` | 同型题 + 共享标签/难度/理由 | `core.similar.find_similar` |
| 4 | `aigotutor_review_queue` | `time_budget_minutes?` | 今日复习队列（FSRS 到期 + 优先级排序 + 理由） | `pipeline.prioritize_review` + 到期查询 |
| 5 | `aigotutor_mastery_profile` | — | 五级画像 + 强弱标签 + 置信度 | `services.get_mastery` + `pipeline.analyze_mastery` |
| 6 | `aigotutor_roadmap` | `weeks?` | 分阶段路线 + 依据 | `pipeline.build_roadmap` |
| 7 | `aigotutor_search_problems` | `keyword`, `difficulty?`, `limit?` | 题目列表（id/标题/难度/标签） | `services.list_problems`（keyword 过滤） |
| 8 | `aigotutor_get_problem` | `problem_id` | 题面/样例/约束（隐藏用例不暴露） | `services.get_problem` + tags |
| 9 | `aigotutor_wrong_book` | `limit?` | 错题列表 + 错因聚类摘要 | `services` 错题查询 + `cluster_errors` |
| 10 | `aigotutor_submit_solution` | `problem_id`, `language`, `code` | 真实判题 verdict + 失败用例摘要 | 判题服务（subprocess 沙箱）+ 提交落库 |
| 11 | `aigotutor_mark_review` | `problem_id`, `rating(1-4)` | FSRS 下次复习间隔 | `services` 复习打分路径 |

**写操作安全**：#10/#11 是仅有的写工具，落库用户 = `AIGOTUTOR_MCP_USER`
指定的用户；判题走既有沙箱（超时/内存限制同样生效）。

### A4. 验收标准

1. Claude Desktop / Cursor 配置示例（文档给出 JSON）后，能自然语言完成
   "推荐题 → 看题面 → 要提示 → 提交判题 → 记复习"完整闭环；
2. `tests/test_mcp.py`：每个工具至少 1 条断言（mock provider 下可跑，
   校验返回结构与治理字段，如 hint 的 strength 与掌握度口径一致）；
3. MCP 进程与 Web 同时运行互不干扰（共享 WAL 库实测）；
4. `mcp` 未安装时 Web 全量测试不受影响；
5. README 增加 MCP 章节（配置示例 + 工具表）。

## 二、Feature B：模拟面试模式

### B1. 背景与目标

对标 Interviewing.io / Final Round AI 等品类的共识形态：**限时作答 +
会话式考官 + 结束后结构化复盘报告**。本项目组件几乎齐备（对话引擎/
判题/质量评分/报告），v1 只做"单题技术面"。

**目标**：
1. 一次 20-40 分钟的单题算法模拟面：考官人设对话（问思路、追问、
   不主动给答案）+ 代码提交实测 + 计时；
2. 结束生成**结构化复盘报告**：规则算客观分（判题/质量/耗时/提示依赖），
   LLM 在窗口内写叙事评语（延续两阶段哲学）；
3. 报告可沉淀（列表查看历史），作为学习报告体系的一部分。

**非目标（v1 不做）**：系统设计面、多题连环面、语音、peer 匹配、
评分对外分享。

### B2. 用户故事

1. 作为求职者，我选定一道题和时限（默认 30 分钟）开始模拟面，
   页面有倒计时但不打断；
2. 面试中考官让我先讲思路，我讲错会被追问暴露矛盾，但**考官不直接
   给答案**（提示默认锁定最弱档，用户主动索要才升一档且计入"提示依赖"）；
3. 我随时可以提交代码，系统真实判题（AC/WA/TLE...），考官会就结果追问；
4. 到时或我主动结束后，生成复盘报告：五维评分 + 逐段时间线 +
   改进建议；
5. 我可以在"模拟面试"页查看历史场次与报告。

### B3. 数据模型（复用优先）

- `chat_sessions` 增列：`kind`（tutor|interview，默认 tutor）、
  `time_limit_minutes`、`meta`（JSON：面试状态/索要提示次数/提交 id 列表）。
  一张迁移完成（`d4b2...`）。**对话消息直接复用 `chat_messages`**——
  面试官也是对话，只是人设与治理策略不同；
- 新表 `interview_reports`：`id/session_id/user_id/problem_id/
  verdict/五维分数(JSON)/narrative(Text)/degraded(Bool)/created_at`。

### B4. 评分 Rubric（规则层算客观分，各 0-100）

| 维度 | 来源 | 规则 |
|---|---|---|
| 正确性 | 判题沙箱 | AC=100；按通过用例比例折算（0 通过=0） |
| 代码质量 | quality Agent 规则分 | 直接采用两阶段评分的规则基线 |
| 提示依赖 | 会话 meta | 0 次=100，每次索要 -25，下限 0 |
| 时间效率 | 计时 | 用时 ≤ 时限 1/2=100，线性衰减到超时=20 |
| 沟通质量 | 对话轮次 | 有效思路陈述轮次占比（规则可解释口径） |

**总分** = 加权（0.35/0.2/0.15/0.15/0.15），叙事评语由 LLM 生成且
**只能引用规则算出的数字**（prompt 中给全部分数，要求逐维点评 +
3 条改进建议；窗口 ±0：分数完全由规则定）。

### B5. API（全部属主校验）

| 接口 | 说明 |
|---|---|
| `POST /api/interview/start` | `{problem_id, time_limit_minutes}` → 创建 interview 会话（kind=interview，考官 system prompt） |
| `POST /api/interview/{id}/message` | 面试对话（复用 chat 消息通道，考官人设 + 禁答案硬规则；`ask_hint=true` 时升档并计数） |
| `POST /api/interview/{id}/submit` | 提交代码判题（记录 submission_id 到 meta，考官下轮得知结果） |
| `POST /api/interview/{id}/finish` | 结束（到时/主动）→ 生成报告（规则分 + LLM 叙事，降级为模板） |
| `GET /api/interview/{id}/report` | 报告详情 |
| `GET /api/interview` | 历史场次列表 |

前端：`InterviewView`（开始面板 / 面试间：对话+代码编辑器+倒计时+提交 /
报告页），路由 `/interview`，入口进侧边栏。

### B6. 验收标准

1. 全流程实测（mock + 真模型各一遍）：开始 → 对话 ≥2 轮 → 提交 WA →
   追问 → 再提交 AC → 主动结束 → 报告五维齐全、叙事引用真实数字；
2. 提示治理：默认 direction；索要才升档；报告"提示依赖"与实际次数一致；
3. 到时自动收卷（后台计时器 + 前端到点调 finish）；
4. 报告 LLM 降级路径可用（叙事=模板，分数照常）；
5. `tests/test_interview.py`：评分规则纯函数全覆盖 + API 主流程 +
   属主校验（他人访问 404）；
6. 覆盖率不跌破 75%，CI 全绿。

## 三、里程碑与风险

| 里程碑 | 内容 | 预估 |
|---|---|---|
| M1 | Feature A 全部（含测试/文档/README） | 1-1.5 天 |
| M2 | Feature B 后端（模型迁移/评分/6 接口/测试） | 1.5 天 |
| M3 | Feature B 前端 + 全链路验证 | 1 天 |

**风险与对策**：
- MCP SDK 版本漂移 → requirements 锁 `mcp>=2.3`；CI 增加"安装后 import
  可用"的轻量检查（不跑完整 stdio 握手，避免 runner 复杂度）；
- 面试叙事评语质量不稳定 → 分数全部规则算定，LLM 只做点评（可降级），
  评估思路与既有 golden set 一致；
- SQLite 多进程写竞争（MCP 与 Web 并发写）→ 均已有 busy_timeout=5000，
  写操作低频，实测覆盖；
- 范围蔓延 → 两个功能各自的"非目标"清单为硬边界，新想法进 backlog。
