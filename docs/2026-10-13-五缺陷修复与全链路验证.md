## 二、缺陷 1 · 默认启动下判题不可用（P0）

### 现象

按 README 的默认命令 `python run.py` 启动后，**任何提交判题都失败**：

```
File "app/judge/subprocess_backend.py", line 331, in _run_process_with_resources
    proc = await asyncio.create_subprocess_exec(
File "C:\python3.13\Lib\asyncio\base_events.py", line 539, in _make_subprocess_transport
    raise NotImplementedError
NotImplementedError
```

`smoke_batch_a.py`（判题验收）直接连不上服务，日志里 `NotImplementedError` 出现 8 次。

### 根因

uvicorn 0.51 的循环选择逻辑（`uvicorn/loops/asyncio.py`）：

```python
def asyncio_loop_factory(use_subprocess: bool = False):
    if sys.platform == "win32" and not use_subprocess:
        return asyncio.ProactorEventLoop   # 只有它支持子进程
    return asyncio.SelectorEventLoop       # Windows 上不支持子进程
```

而 `use_subprocess = bool(reload or workers > 1)`（`config.py:377`）。

于是：**`run.py` 默认 `RELOAD=1` → uvicorn 选 Selector 循环 → 判题子进程直接抛 `NotImplementedError`**。
判题沙箱正是靠 `create_subprocess_exec` 执行用户代码，因此必然 500。

> 为什么之前没被发现：上一轮验收是**不带 reload** 启动的（日志里没有 reloader 行），
> 所以 132 项端到端全绿。**"测试通过"与"默认用法可用"是两件事。**

### 修复（两层防线）

**第一层 · `run.py` 钉住事件循环**（治本）：

```python
kwargs: dict[str, object] = {}
if sys.platform == "win32" and reload:
    # Windows + reload 必须钉住 Proactor，否则判题不可用
    kwargs["loop"] = "asyncio:ProactorEventLoop"
uvicorn.run("app.main:app", host="0.0.0.0", port=port, reload=reload, **kwargs)
```

**第二层 · 判题后端运行时自检**（防其他启动方式绕过）：

```python
# app/judge/subprocess_backend.py
def loop_supports_subprocess() -> tuple[bool, str]:
    """当前事件循环是否支持创建子进程。"""
    if not IS_WINDOWS:
        return True, ""
    loop = asyncio.get_running_loop()
    if isinstance(loop, asyncio.ProactorEventLoop):
        return True, ""
    return False, "当前事件循环不支持子进程…请用 `python run.py` 启动…"
```

`judge()` 开头预检 → 不支持时返回 **IE + 可操作指引**，而不是裸抛异常；
`availability()` 同步上报 `available=false` + 原因 → 设置页与 `/api/judge` 都能看到。

### 验证

| 场景 | 结果 |
|---|---|
| `python run.py`（reload 开启） | reloader 进程在跑，**判题 18/18 通过，零异常** |
| 文件改动触发热重载后 | 判题仍 18/18 通过（Proactor 与 WatchFiles 共存） |
| 全套端到端 | **132/132 全绿**（此前该场景下 batch_a 完全失败） |

## 三、缺陷 2 · `failed_case` 永远为空（死代码）

### 现象

提交 WA 代码后，`judge_detail.cases` 有完整的失败用例信息（含 stdout），
但顶层 `failed_case` 字段恒为空字符串，错题本与 judge Agent 的归因都拿不到失败用例内容。

### 根因

`app/judge_service.py:171`：

```python
if first_fail is not None and not first_fail.case_id.startswith(""):
```

**空字符串的 `startswith("")` 恒为 `True`**，取反后恒为 `False` → 整块赋值成为死代码。

```python
>>> "".startswith("")
True
>>> not "".startswith("")
False
```

### 修复

去掉恒假条件（保留 `first_fail is not None` 判断）：

```python
if first_fail is not None:
    case_obj = next((c for c in cases if c.id == first_fail.case_id), None)
    if case_obj is not None and not case_obj.hidden:
        failed_case = (f"[用例 {case_obj.order_no}]\n输入:\n{case_obj.input_data}\n"
                       f"期望:\n{case_obj.expected_output}\n实际:\n{first_fail.stdout}")
    else:
        failed_case = f"[隐藏用例 {case_obj.order_no if case_obj else '?'}] 未通过"
```

回归测试 `test_sandbox_reports_failed_case_detail` 直接查库断言内容非空。

## 四、缺陷 3 · auto 回退提示永不出现（死代码）

### 现象

`judge_mode=auto` 且题目没有测试用例时，系统正确回退为「调用方判定」，
但**不附带任何说明** —— 用户会误以为调用方传来的 verdict 是判题机的真实结论。

### 根因

`app/api/submissions.py` 中，`mode` 变量在回退分支**已被改写**：

```python
mode = body.judge_mode
if mode == "auto":
    mode = "sandbox" if case_count > 0 else "caller"   # ← mode 在这里被改成 "caller"

if mode == "sandbox":
    ...
else:
    ...
    if case_count == 0 and mode == "sandbox":   # ← 此时 mode 恒等于 "caller"，永假
        verdict_fields["judge_detail"] = {..., "message": "该题未配置测试用例，已回退为调用方判定"}
```

### 修复

判断**请求时的原始模式**（`body.judge_mode`）而非被改写的局部变量：

```python
if case_count == 0 and body.judge_mode == "auto":
```

回归测试 `test_auto_fallback_attaches_reason` 断言响应里含「回退」字样。

> 修完后做题页会明确显示「本题未配置测试用例，提交将使用"调用方判定"模式」——
> 已在浏览器实测确认。

## 五、缺陷 4 · 全站时间显示偏 8 小时

### 现象

刚提交的记录在页面上显示「**8 小时前**」。本地时间 17:33 提交，界面说 8 小时前。

### 根因

数据库用 SQLAlchemy `DateTime`（SQLite 无时区列）存 UTC 时间，
**读出来是 naive datetime**，API 原样输出：

```
GET /api/submissions →
{"created_at": "2026-10-13T09:33:40.103483"}    ← 无 Z 后缀
```

前端 `new Date("2026-10-13T09:33:40.103483")` 按 **本地时间（东八区）** 解析：

```js
const d = new Date('2026-10-13T09:33:40.103483');   // 解析为本地 09:33
(Date.now() - d.getTime()) / 3600000                 // → 8.03 小时
```

影响面：**全站时间展示** —— 提交记录、做题页历史、错题本、复习队列、管理后台、设置页。

### 修复（数据层统一语义）

新增 `UTCDateTime` TypeDecorator，写入转 naive UTC、**读取补回 UTC 时区**：

```python
class UTCDateTime(TypeDecorator):
    impl = DateTime
    cache_ok = True

    def process_bind_param(self, value, dialect):
        if value is not None and value.tzinfo is not None:
            value = value.astimezone(timezone.utc).replace(tzinfo=None)
        return value

    def process_result_value(self, value, dialect):
        if value is not None and value.tzinfo is None:
            return value.replace(tzinfo=timezone.utc)
        return value
```

把 9 处时间列（`created_at` / `updated_at` / `last_login_at` / `due_at` /
`last_review_at` / `last_wrong_at` / `finished_at` / `read_at` / `last_practiced_at`）
全部换成 `UTCDateTime`。

**为什么修在数据层而不是前端**：时间戳语义属于数据层。任何消费者（前端、脚本、
第三方对接）都应拿到无歧义的 UTC；只改前端等于把语义问题推给每一个调用方。

**存储格式不变**（仍是 naive UTC 字符串），因此**无需数据迁移**。

### 验证

```
修复前: "created_at": "2026-10-13T09:33:40.103483"
修复后: "created_at": "2026-10-13T09:33:40.103483Z"     ← 带 Z，前端按 UTC 解析
```

界面实测：同一提交从「8 小时前」变为「10 分钟前」（正确）；管理后台时间从
`09:29` 变为 `17:29`（本地时间，正确）。

回归测试：`test_api_timestamps_carry_utc_marker`、`test_utc_datetime_roundtrip_is_aware`。

## 六、缺陷 5 · 设置页"服务健康"永远异常

### 现象

设置页「运行态」卡片显示 **服务健康：异常**（红色），页面底部还弹 `Not Found`。
但 `/health` 实际返回 `{"status":"ok","db":true}` —— 服务完全正常。

### 根因

前端 API 层统一加 `/api` 前缀（`http.ts` 的 `baseURL: '/api'`），
因此 `http.get('/health')` 实际请求 **`/api/health`**；

而后端只注册了裸路径 `/health`（`app/api/data.py:110`）→ **404**。

```bash
$ curl http://127.0.0.1:8000/api/health
{"detail":"Not Found"}
$ curl http://127.0.0.1:8000/health
{"status":"ok","app":"AIgoTutor","db":true,"default_provider":"mock"}
```

### 修复

`/health` 被 Dockerfile、两个 compose、CI 的 HEALTHCHECK 依赖（**不能改**），
因此**同时注册两个路径**，共用同一实现：

```python
async def _health_payload() -> dict: ...

@health_router.get("/health", response_model=dict)          # 探针路径，保持不变
async def health():
    return await _health_payload()

@health_router.get("/api/health", response_model=dict, include_in_schema=False)
async def health_api_alias():                                # 前端路径
    return await _health_payload()
```

回归测试 `test_health_available_on_both_paths` 同时断言两个路径。

## 九、遗留与注意

1. **数据库累积了大量测试残留**：65 用户 / 89 题目，其中 37 道题缺测试用例。
   均为冒烟与验收脚本产生（`冒烟题-*`、`流式题-*`、`前端验收题-*`、`batch*`/`web*`/`smoke*` 用户）。
   **演示前建议清库重建**：`python -m scripts.seed --reset`。
   管理后台的「数据清理」与「题库体检」也能处理。

2. **`code-block` 无可见滚动条**：结果 JSON 超宽时可横向滚动（CSS 已设 `overflow-x: auto`），
   但滚动条样式在部分浏览器下不可见，用户可能不知道可以滚。非缺陷，属可用性优化项。

3. **Windows + reload 的坑已双重防护**，但仍建议生产用 `RELOAD=0`（Docker/compose 已是如此）：
   Proactor 是 workaround 性质的兼容层，无 reload 时链路最短。

4. **`UTCDateTime` 只影响读取语义，不改变存储格式**，因此**不需要迁移**；
   但若有外部系统直接读 SQLite 文件，需知道库里是 naive UTC。

5. **测试残留的 `_probe_reload_proactor.py`**（本轮验证用）已在提交前删除。
